# Команды запуска

Всё запускается внутри контейнера. Поднять его — `./run.sh` (второй и третий
терминал — та же команда, она подключится к уже работающему).

## Сборка образа

```bash
cd ~/Nav_Test
docker build -f docker/Dockerfile -t nav2:jazzy .
```

Запускать обязательно из `Nav_Test/`, а не из `docker/`: контекст сборки — это `.`,
от него считается путь в `COPY docker/entrypoint.sh`.

## Симулятор с лидаром (исходный стенд)

```bash
ros2 launch maze_nav maze.launch.py                 # лабиринт maze1 + TurtleBot3
ros2 launch maze_nav maze.launch.py gui:=false      # без окна, только физика
ros2 launch maze_nav maze.launch.py world:=maze2.world x_pose:=-3.75 y_pose:=-3.75
```

# Навигация по RGB-D (ветка rgbd-nav)

## Этап 1. RTAB-Map на датасете TUM RGB-D

Опорная точка перед симулятором: прогон на данных с ground truth. Если здесь
ошибка в пределах нормы, дальнейшие провалы можно списывать на данные и камеру,
а не на сам алгоритм.

### 1. Скачать датасет

```bash
mkdir -p ~/Nav_Test/datasets && cd ~/Nav_Test/datasets
curl -L -C - --retry 20 --retry-all-errors \
  -O https://vision.in.tum.de/rgbd/dataset/freiburg3/rgbd_dataset_freiburg3_long_office_household.bag
```

1.6 ГБ. `-C -` обязателен: докачка нужна, если соединение рвётся (например,
через локальный прокси). Проверить целостность — размер должен быть
ровно `1700571628` байт:

```bash
stat -c%s rgbd_dataset_freiburg3_long_office_household.bag
```

### 2. Сконвертировать в ROS 2

Штатный рецепт RTAB-Map требует ROS 1 (`rosbag decompress`, `roscore` и два
ROS1-скрипта). Вместо него — свой конвертер, ROS 1 не нужен:

```bash
./run.sh python3 /root/ros_ws/src/maze_nav/scripts/tum_bag_to_ros2.py \
  /datasets/rgbd_dataset_freiburg3_long_office_household.bag
```

Занимает несколько минут. Ключ `--force` перезаписывает результат,
`--keep-all-topics` оставляет `/cortex_marker_array` (по умолчанию он
выбрасывается — RTAB-Map его не читает, а весит он треть бэга).

Проверить результат:

```bash
./run.sh ros2 bag info /datasets/rgbd_dataset_freiburg3_long_office_household
```

Ожидается 5 топиков, 22395 сообщений, 87.3 с. Тип `/tf` должен быть
`tf2_msgs/msg/TFMessage`, а не ROS1-овский `tf/msg/tfMessage`.

### 3. Прогнать RTAB-Map

Собрать пакет и запустить в первом терминале:

```bash
./run.sh
colcon build --symlink-install && source install/setup.bash
ros2 launch maze_nav rtabmap_tum.launch.py
```

Во втором терминале:

```bash
./run.sh
ros2 bag play /datasets/rgbd_dataset_freiburg3_long_office_household --clock
```

`--clock` обязателен: launch поднимает узлы с `use_sim_time:=true`.

Аргументы launch:

* `viz:=true` — включить GUI `rtabmap_viz` (нужен X11);
* `database_path:=...` — куда класть базу, по умолчанию `/datasets/rtabmap_tum.db`;
* `publish_camera_tf:=true` — публиковать статику `kinect -> openni_rgb_optical_frame`.
  **По умолчанию выключено и включать не надо.** Подробности — в README.

### 4. Снять отчёт

После остановки launch по Ctrl+C:

```bash
./run.sh env QT_QPA_PLATFORM=offscreen rtabmap-report --loop /datasets/rtabmap_tum.db
```

`QT_QPA_PLATFORM=offscreen` обязателен: `rtabmap-report` — Qt-приложение,
а в образе выставлен `QT_QPA_PLATFORM=xcb`, и без переопределения оно падает
с «could not connect to display».

Полезные ключи: `--poses` выгружает траектории (одометрия, оптимизированный
граф, ground truth) в формате TUM RGB-D — их можно скормить `evo_ape`.

Сводка по базе без Qt:

```bash
./run.sh rtabmap-info /datasets/rtabmap_tum.db
```

### Что должно получиться

```
rtabmap_tum.db (137, 20.0 m): RMSE= 0.020 m (max=0.053m, odom=0.059 m) ang=0.9 deg,
slam: avg=54 ms (max=173 ms) loops=16 (t_err=0.017m r_err=0.55 deg),
odom: avg=41ms (max=60ms)
```

На что смотреть:

* `loops=16` — замыкания петли срабатывают. Если здесь 0, RTAB-Map работает
  как чистая одометрия, и смысла в нём нет;
* `RMSE=0.020 m` против `odom=0.059 m` — SLAM втрое точнее голой одометрии,
  значит замыкания не просто находятся, но и исправляют траекторию;
* `odom: avg=41ms` — одометрия успевает за 24 Гц, то есть реальное время.

### 5. Посмотреть глазами

Три способа, от самого дешёвого к самому подробному.

**Готовые графики траекторий.** Ничего запускать не надо, картинки уже лежат
в `datasets/`: `traj_trajectories.png` (вид сверху: эталон, SLAM, одометрия),
`traj_xyz.png`, `traj_rpy.png`, `traj_speeds.png`.

Пересобрать их можно так:

```bash
./run.sh bash -c '
  source /opt/ros/jazzy/setup.bash
  export QT_QPA_PLATFORM=offscreen MPLBACKEND=Agg
  cd /datasets
  rtabmap-report --poses /datasets/rtabmap_tum.db
  # rtabmap-report пишет заголовок "#timestamp ..." и девятую колонку id,
  # а evo требует ровно 8 полей без заголовка — приводим к его формату
  for f in gt odom slam; do
    grep -v "^#" rtabmap_tum_$f.txt | awk "{print \$1,\$2,\$3,\$4,\$5,\$6,\$7,\$8}" > evo_$f.txt
  done
  evo_traj tum evo_slam.txt evo_odom.txt --ref evo_gt.txt \
    --plot_mode xy --save_plot /datasets/traj
  evo_ape tum evo_gt.txt evo_slam.txt -a
'
```

**Разбор готовой базы.** `rtabmap-databaseViewer` — отладчик, а не плеер:
нужен, когда что-то не сошлось и надо понять почему.

```bash
xhost +local:docker
./run.sh rtabmap-databaseViewer /datasets/rtabmap_tum.db
```

Первым делом — `View -> Concise Layout`, иначе окно открывает разом девять
панелей. Разбор интерфейса и остальных утилит RTAB-Map — в [RTABMAP.md](RTABMAP.md).

**Живая демонстрация (то, что показывают в роликах).** Картинка с камеры
с отслеживаемыми признаками, накапливающееся 3D-облако и вспыхивающие замыкания
петли. Бэг проигрывается сам, второй терминал не нужен:

```bash
xhost +local:docker          # один раз на хосте
./run.sh
# дальше внутри контейнера:
colcon build --symlink-install && source install/setup.zsh
ros2 launch maze_nav rtabmap_tum.launch.py viz:=true play:=true rate:=0.5
```

Пересборка нужна после любой правки launch-файлов и скриптов: артефакты
`colcon` лежат в именованных томах `nav2_build`/`nav2_install`, а не на хосте,
и сами по себе от изменений в `src/` не обновляются. Оболочка в контейнере —
zsh, поэтому `setup.zsh`, а не `setup.bash`.

* `play:=true` — проигрывать бэг самим, не открывая второй терминал. Старт
  отложен на 8 секунд: узлы поднимаются не мгновенно, а сообщения, пришедшие
  до подписки, просто пропадут, и первые секунды датасета выпадут из карты;
* `rate:=0.5` — вдвое медленнее, чтобы успевать смотреть. `rate:=2.0` наоборот;
* `bag:=...` — другой датасет.

На что смотреть в окне `rtabmap_viz`:

* верхняя панель — кадр с камеры, жёлтым отмечены отслеживаемые признаки.
  Когда их мало (пустая стена, резкий поворот), одометрия близка к срыву —
  именно это будет главной проблемой в сером лабиринте на этапе 2;
* центральная 3D-панель — карта, которая достраивается по ходу;
* в момент замыкания петли граф «дёргается»: накопленный дрейф схлопывается,
  и облако выравнивается. На этом датасете такое случится 16 раз.

Если нужны два терминала по отдельности (например, чтобы перезапускать бэг
без перезапуска SLAM), `play` не указывай:

```bash
./run.sh                     # терминал 1
colcon build --symlink-install && source install/setup.zsh
ros2 launch maze_nav rtabmap_tum.launch.py viz:=true

./run.sh                     # терминал 2
ros2 bag play /datasets/rgbd_dataset_freiburg3_long_office_household --clock
```

X11 в `run.sh` уже настроен (проброс `$XAUTHORITY` и `/tmp/.X11-unix`),
отдельно ничего доставлять не нужно.

## Этап 2. Навигация по RGB-D в Gazebo, без лидара и колёсной одометрии

```bash
xhost +local:docker          # один раз на хосте
./run.sh
colcon build --symlink-install && source install/setup.zsh
ros2 launch maze_nav rgbd_sim.launch.py nav2:=true
```

Аргументы:

* `nav2:=true` — поднять стек Nav2 (по умолчанию только симулятор и RTAB-Map);
* `viz:=true` — окно `rtabmap_viz` с живой картой и признаками;
* `gui:=false` — без окна Gazebo, только физика;
* `world:=...` — другой мир. По умолчанию `turtlebot3_house.world`: у него есть
  настоящие текстуры. **Серый `maze1.world` не годится** — в нём ни одной
  текстуры, и визуальная одометрия слепа;
* `x_pose:`, `y_pose:` — точка спавна.

### Отправить цель

Во втором терминале:

```bash
./run.sh
ros2 action send_goal /navigate_to_pose nav2_msgs/action/NavigateToPose \
  "{pose: {header: {frame_id: map}, pose: {position: {x: 0.0, y: 0.5}, orientation: {w: 1.0}}}}"
```

**Внимание про координаты.** Начало координат карты RTAB-Map — это стартовая
поза робота, а не начало мира Gazebo. Если робот заспавнен в `world(-2.0, 0.5)`,
то цель `map(0.0, 0.5)` окажется в `world(-2.0, 1.0)`. Не перепутать при сверке
с ground truth.

### Посмотреть в RViz

```bash
./run.sh rviz2
```

Что добавить: `Map` на `/map`, `PointCloud2` на `/cloud`, костмапы на
`/local_costmap/costmap` и `/global_costmap/costmap`, `TF`.

### Проверить, что всё живо

```bash
ros2 topic hz /camera/image_raw /odom /cloud /local_costmap/costmap
ros2 run tf2_ros tf2_echo map odom          # даёт RTAB-Map
ros2 run tf2_ros tf2_echo odom base_footprint   # даёт визуальная одометрия
```

Если `odom -> base_footprint` нет — одометрия не поехала. Колёсной одометрии
в этой сборке нет намеренно, подменить её некому.

### Ожидаемый результат

```
Goal finished with status: SUCCEEDED
одометрия: quality около 500, потерь 0
карта: примерно 200x150 клеток после короткого проезда
```

# Этап 4. Робот из CAD: меканум-привод в Gazebo

Здесь ездит уже не TurtleBot, а настоящий робот: описание собрано из
STEP-модели, меканум-колёса считаются честно — по двенадцать свободных
роликов на колесо, сорок восемь тел на робота.

## Запуск

```bash
./run.sh                                        # терминал 1
ros2 launch maze_nav drive_robot.launch.py

./run.sh                                        # терминал 2 — подключится к тому же контейнеру
ros2 run teleop_twist_keyboard teleop_twist_keyboard
```

Боковое движение — на **заглавных** буквах: `J` влево, `L` вправо, `U` и `O`
по диагонали. Строчные `j` и `l` разворачивают на месте. Скорости меняются
клавишами `q` и `z`.

Полезные аргументы:

```bash
ros2 launch maze_nav drive_robot.launch.py gui:=false   # без окна Gazebo
ros2 launch maze_nav drive_robot.launch.py rviz:=true   # плюс RViz
ros2 launch maze_nav drive_robot.launch.py world:=maze1.world
```

Посмотреть описание без физики и симулятора:

```bash
ros2 launch maze_nav display_robot.launch.py
```

## Ожидаемый результат

Замерено против истинной позы из Gazebo, команда 0.3 м/с и 0.5 рад/с:

```
вперёд    dx=+0.63  dy=-0.006  dyaw=-0.003
влево     dx=+0.002 dy=+0.689  dyaw=+0.004
вправо    dx=-0.005 dy=-0.697  dyaw=-0.006
разворот  dx=-0.003 dy=+0.001  dyaw=+1.100
```

Колёсная одометрия против истины: вперёд 0.4 %, разворот 0.3 %, вбок 6.4 %.
Шесть процентов вбок — это настоящее проскальзывание меканума, а не ошибка:
боком он всегда едет хуже всего. Темп симуляции 0.985 от реального времени.

## Пересборка описания

URDF генерируется, править его руками бессмысленно — перезатрётся:

```bash
python3 src/maze_nav/scripts/gen_robot_urdf.py \
    src/maze_nav/urdf/wheels_from_cad.json \
    -o src/maze_nav/urdf/agro_robot.urdf.xacro
```

Меш корпуса пересобирается из STEP (самого STEP в репозитории нет, он
не нужен для запуска — только для переделки геометрии):

```bash
env -u LOCPATH freecadcmd src/maze_nav/scripts/cad_chassis_mesh.py -- \
    робот.step src/maze_nav/urdf/wheels_from_cad.json \
    src/maze_nav/meshes/chassis.stl
```

`env -u LOCPATH` обязателен, если запускать из терминала VS Code, поставленного
снапом: он подсовывает свой `LOCPATH`, и FreeCAD падает с
`undefined symbol: __libc_pthread_init`.

## Про раскладку роликов

URDF генерируется с раскладкой роликов, **зеркальной** к STEP-модели.
Это единственное осознанное расхождение с CAD, и вот почему.

Плечо, с которым меканум создаёт момент разворота, равно полубазе плюс
полуколея или полубазе минус полуколея — знак задаёт рука ролика.
В STEP рука такая, что получается разность: `|0.3178 − 0.3554| = 3.8 см`
против 67 см у общепринятой раскладки, в восемнадцать раз меньше. Робот
с такими колёсами разворачивается не качением, а юзом. Замерено: одометрия
по развороту врала на 40 %, при езде вбок уводило на 0.18 рад, темп
симуляции падал до 0.73.

Похоже, в CAD на все четыре угла поставлено колесо одной руки. Проверяется
на железе за десять секунд: у исправного меканума пары по диагонали
наклонены одинаково, а сами диагонали — по-разному.

Если окажется, что железо собрано как в CAD:

```bash
python3 src/maze_nav/scripts/gen_robot_urdf.py ... --roller-layout cad
```

и переставить перёд с задом в `params/agro_controllers.yaml` — там написано,
как именно.

# Этап 5. Заезд на рельсы

Сцена повторяет стенд, снятый на видео для датасета YOLO: настил из листов
фанеры метр на метр, на нём лежит П-образный конец рельсов, дальше трубы
идут на опорах.

```bash
ros2 launch maze_nav drive_robot.launch.py world:=rails.world
```

Робота launch ставит сам — в середину настила и чуть выше его верха
(см. таблицу `SPAWN` в launch-файле). Перебить можно как обычно,
`x:=… y:=… z:=…`. Дальше вперёд телеопом.

## Размеры и откуда они

Всё измерено по кадру с глубиной из того же стенда, а не взято из головы.
Метод: по облаку точек подогнана плоскость фанеры, кадр перепроецирован в
ортофото с масштабом 1 пиксель = 1 мм, а размеченный человеком контур
рельса из датасета спроецирован на ту же плоскость.

Две проверки масштаба сошлись сами собой: колея получилась 545 мм при
роликах робота на 543, а толщина перемычки на контуре — 52 мм при трубе 51.

| величина | значение |
|---|---|
| труба | Ø51 мм, стенка 2.0 мм |
| колея по осям | 545 мм |
| радиус угла П по оси | 145 мм (2.8 диаметра) |
| прямая перемычка | 255 мм |
| вылет П на фанеру | 210 мм от кромки до внешней грани |
| лист фанеры | 1000 x 1000 мм |
| настил по умолчанию | 2 x 2 листа, верх 120 мм |
| опоры за фанерой | высота 120 мм, шаг 1.25 м |

Ближний конец — именно **П**, а не полукруг: скруглённый угол, прямой
участок, скруглённый угол. Радиус считается однозначно из того, что у П
прямой участок внешней грани ровно такой же длины, как у осевой линии.

Отсюда следует любопытное: прямые рельсы начинаются на 40 мм раньше кромки
фанеры, то есть П занимает почти весь свой вылет.

## Главное в геометрии заезда

```
меканум-колесо      R = 101.4 мм
рельсовый ролик     R =  50.0 мм   (дорожка качения)
разница                  51.4 мм   <- труба ровно 51 мм
```

Разница радиусов равна диаметру трубы. Поэтому **высота фанеры на заезд не
влияет**: важно лишь, что труба лежит НА той же поверхности, по которой
катятся меканум-колёса, а не утоплена в неё. Робот при передаче опоры
опускается на 0.4 мм, и так при любой высоте.

Утопить трубу заподлицо нельзя — ролику будет не за что зацепиться.
Заехать боком меканумом тоже нельзя: реборда R=75 мм висит на 146 мм от
пола, верх трубы на 171 мм, она в трубу упрётся. Заезд только продольный.

Запас у манёвра около 40 мм с обеих сторон. Передние колёса сходят с кромки
фанеры через 40 мм после того, как передние ролики встают на прямой рельс;
задние колёса сходят через 40 мм после того, как задние ролики миновали П.

## Ожидаемый результат

```
 x, м    y, мм   z, мм   курс   | что под колёсами
-1.001     -1   +119.9          | старт, launch ставит сам
-0.369     -4   +120.1  -0.45   | фанера
-0.138     -6   +119.8  -0.32   | перед за кромкой
+0.459     -6   +119.9  -0.55   | РЕЛЬСЫ
+1.443     -8   +119.9  -0.12   | РЕЛЬСЫ
+2.766     -8   +119.9  -0.04   | РЕЛЬСЫ
```

119.9 мм — расчётная посадка на рельсы (221.0 - 101.4), настил на 120.0.
Курс за весь заезд не уходит дальше 0.7°, на рельсах реборды доводят его
до сотых долей градуса. Темп симуляции 1.0.

Если на переходе появится заметный рывок, первым делом смотреть на дугу
скругления: звено там ставится вдоль КАСАТЕЛЬНОЙ к дуге, а не по углу
самой дуги, и эти два угла расходятся ровно на 90°. С перепутанными углами
звенья встают поперёк, дуга рассыпается ёлочкой, и робота кидает на 4°.
Проверить можно по координатам из мира: все звенья должны лежать на одном
радиусе.

## Пересборка сцены

```bash
python3 src/maze_nav/scripts/gen_rails_world.py -o src/maze_nav/worlds/rails.world
```

Ключи: `--gauge`, `--bend-radius`, `--pipe-od`, `--deck-height`, а также
`--sheet`, `--sheets-x`, `--sheets-y` для размера настила. Все значения по
умолчанию — замеренные.

Настил набран листами метр на метр, как в жизни: два листа вдоль нужны,
чтобы робот (колёсная база 636 мм, корпус 1.2 м) стоял на нём целиком и
успевал разогнаться до рельсов. Вылет рельсов на настил от размера настила
не зависит — он отмерян от дальней кромки.

## Поиск рельсов: пока оракул, потом CV

Настоящего распознавания рельсов нет. Его временно заменяет
`scripts/rail_oracle.py`: он берёт истинную геометрию труб из файла мира и
рисует маску тех пикселей кадра, куда труба проецируется. Включён по
умолчанию, отключается ключом `rail_oracle:=false`.

Интерфейс выбран такой же, какой вернёт модель CV, — одноканальная маска
`/rails/mask` размером с кадр глубины. Поэтому замена оракула на модель это
правка одной подписки, а не переделка потребителя.

Маска строится через буфер дальности, а не простым диском по осевой линии.
Камера смотрит сверху под углом и видит верх и ближний бок трубы, которые
проецируются шире осевого радиуса, — с чистым диском 10% пикселей трубы
оставались снаружи. Просто раздуть диск нельзя: он перехлёстывает на пол за
кромкой настила, и доля попаданий падает с 95 до 71%. Поэтому диск рисуется
с запасом в буфер дальности, а в маску идут только пиксели, где измеренная
глубина совпала с трубой. Заодно бесплатно получается перекрытие: за
препятствием глубина не совпадёт. Замерено: маска накрывает 98.7% пикселей
на высоте трубы, поперечный размах маски −297..+301 мм при осях труб ±272 и
радиусе 25.5 мм.

Привязка к миру берётся один раз на старте разовым запросом позы робота у
Gazebo. Позу на момент снимка оракул берёт из истории `/odom` по метке
времени, а не через TF: одометрия публикуется после обработки кадра и
отстаёт от него примерно на полкадра, поэтому запрос TF на точную метку
упирается в экстраполяцию в будущее, а ждать внутри обработчика нельзя —
исполнитель однопоточный и заблокирует сам себя.

**На чём оракул мерить нельзя.** Он не воспроизводит ошибок распознавания,
пропусков на бликах и ложных срабатываний. Дальность обнаружения рельсов,
устойчивость к шуму и точность выхода на позицию проверяются только с
настоящей моделью. Оракул нужен, чтобы отладить логику заезда отдельно от
качества детектора.

## Цвета на карте

RTAB-Map сливает кромку, рельсы и прочие препятствия в одно облако
`/cloud_obstacles`, а RViz красит слой целиком. Поэтому цвет везётся в самих
точках, в поле `rgb`, а слой переключён на `Color Transformer: RGB8`:

* красный — виртуальная кромка настила, поднятая на 0.30 м;
* зелёный — рельсы по маске;
* светло-серый — прочие препятствия.

Две тонкости, без которых цвет не доживает до карты. Первая: сетка RTAB-Map
усредняет цвет в вокселе 5 см, и труба шириной 51 мм внутри такой клетки
всегда в меньшинстве — вместо зелёного выходит (125,207,142). Поэтому точки
пола ближе 10 см к рельсу в облако не идут: клетку всё равно занимает труба.
Вторая: облако прореживается медианой высоты по клетке 5 см, причём рельсы
медианятся отдельно от пола, иначе тонкую трубу пересилят точки пола.

Медиана нужна ещё и сама по себе. Шум дальномера растёт как квадрат
дальности, и на двух метрах его 95-й процентиль равен +30 мм — ровно порог
`Grid/MaxGroundHeight`. Без медианы каждая двадцатая точка перещёлкивалась в
препятствие, и по дальнему краю обзора высыпала ложная сыпь.


## Граница обрыва: почему заполнение, а не линия

Сначала на карту шла только ЛИНИЯ края, а пол за кромкой подтягивался к
опорной плоскости — он ведь проезжий, просто с другого уровня. Для стенда
это неверно и опасно: площадь за краем настила ложилась на карту
**свободной**, и единственным, что удерживало планировщик, оставалась тонкая
линия. А линия пунктирная. Замерено по периметру настила отрезками по 10 см,
после полного оборота на месте:

| дальность от робота | закрыто линией | закрыто заполнением |
|---|---|---|
| 0.0–1.0 м | 100% | 100% |
| 1.0–1.5 м | 76% | 95% |
| 1.5–2.0 м | 42% | 100% |
| 2.0–2.5 м | 50% | 69% |

Любая дыра в линии для Nav2 — это проход прямо в размеченную свободной
область за краем. Поэтому нижний уровень поднимается на виртуальную высоту
0.30 м, и за кромкой получается сплошная стена.

Поднимается не весь видимый нижний уровень, а **полоса шириной 0.40 м**
вдоль кромки (`dropoff_band`). Поднимать всё — верно, но непомерно: красным
заливается всё поле зрения, и карта перестаёт читаться. Полоса закрывает те
же дыры, а за ней точек нет вовсе — то есть неизвестность, которая для Nav2
безопаснее пола, размеченного свободным.

Ширина полосы отмеряется от точек самого настила, а не от найденной линии
края: линия местами рвётся, и полоса порвалась бы вместе с ней, а настил
виден сплошняком.

Заполнение целиком выключается параметром `dropoff_fill`, если появятся
площадки разной высоты, между которыми и правда надо ездить.

Недобор на 2.0–2.5 м — это дальняя кромка настила, её из одной точки видно
плохо. Она достраивается по мере подъезда: детектор работает покадрово, и
каждый новый ракурс досыпает точки.

Оставшиеся незакрытыми отрезки на 1.0–1.5 м — ровно коридор рельсов,
`x=0, y=-0.25..+0.35`. Там границы нет намеренно: при неудачном заезде робот
стоит НА рельсах, то есть за кромкой, и сплошная стена вокруг не дала бы ему
отъехать назад по карте.

Пробовал закрывать пунктир интерполяцией по столбцам кадра — не помогло,
покрытие не изменилось (76/42/50 против 72/42/50). Провалы оказались не
одиночными срывами, а систематическими.


## Заезд на рельсы: Nav2 и собственное управление

Автомат — `scripts/rail_entry.py`. Последовательность: ОСМОТР -> ПОИСК ->
ПОДХОД -> ВЫВЕРКА -> ЗАЕЗД -> ОТКАТ с повтором.

Пересобрать (нужно один раз после обновления, дальше скрипты подхватываются
по ссылке):

```bash
./run.sh colcon build --symlink-install --packages-select maze_nav
```

Первый терминал — сцена, карта и навигация:

```bash
./run.sh ros2 launch maze_nav drive_robot.launch.py \
    world:=room.world slam:=true nav2:=true rviz:=true random_spawn:=true
```

Второй терминал — сам автомат заезда:

```bash
./run.sh ros2 run maze_nav rail_entry.py --ros-args -p use_sim_time:=true \
    -r cmd_vel:=/cmd_vel -r odom:=/odom -r imu:=/imu/data \
    -r obstacles:=/cloud_obstacles
```

`random_spawn:=true` ставит робота в случайную позу на настиле. Чтобы
повторить конкретный прогон, добавь `seed:=7` — это тот случай, на котором
робот раньше падал. Без `random_spawn` робот встаёт в середину настила.

Полезные ключи автомата: `-p drive_distance:=5.0` (дальше проехать по
трубам), `-p retries:=5`, `-p drive_speed:=0.08`.

**Nav2 ведёт только ПОДХОД** — проезд по настилу к точке старта. Там он на
своём месте: есть карта, есть препятствия, робот меканумный и доезжает
боком. Сам ЗАЕЗД идёт напрямую, по двум причинам. При переходе на рельсы
радиус качения падает со 101.4 до 50 мм, робот идёт примерно вдвое медленнее
скомандованного, и регулятор, считающий это отставанием, начал бы
разгоняться. И на рельсах свободы манёвра нет: доворот допустим в пределах
±10°, всё сверх того — промах, который надо признать и повторить.

Успех определяется одним признаком: продвигается робот или стоит. Знать
правильную скорость не нужно и вредно — при заезде робот подкренивается и
может застрять в этом положении.

Рельсы автомат берёт из карты препятствий по ЦВЕТУ: зелёные точки — рельсы,
их пометил детектор по маске сегментации. Это единственное место, где
автомат зависит от распознавания, и при замене оракула на модель CV менять
здесь нечего.

### Что показал прогон

Заезд удался с первой попытки. По наземной правде Gazebo робот встал на
`x = +0.325` (кромка настила на нуле, то есть он на рельсах), поперечное
смещение `y = -7.0 мм` при допуске ±18 мм, курс -0.14°, крен -0.01°.

В журнале заезда прямо видно место перехода на рельсы: до 1.05 м робот шёл
по 108-119 мм за секундное окно при команде 120 мм, после — по 68-77 мм.
Это и есть падение радиуса качения вдвое. Ровно поэтому порог «стоим или
едем» стоит на 0.15 от скомандованного: рабочая точка после перехода 0.58,
а до него 0.92, и оба значения далеко от порога.

### Чего автомат не умеет

Колея, измеренная по видимым точкам, вышла 486 мм против настоящих 545:
рельсы видны частично, и средние двух ниток смещаются внутрь. На заезд это
не повлияло, потому что используется ось, а не колея, но опираться на
измеренную колею нельзя. Начало рельсов тоже найдено консервативно, на 0.2 м
ближе к роботу, чем на самом деле, — в запас, а не в риск.

## Стоянка робота на карте

Камера начинает видеть примерно с 0.6 м, поэтому площадь прямо под роботом
не наблюдается никогда. Раньше она оставалась неизвестной, а для Nav2
неизвестность непроезжая: замерено — клетка под роботом имела стоимость -1,
вокруг 226 неизвестных клеток из 676, планировщик отказывался строить путь
от такого старта, и цель падала с «Goal failed».

Детектор теперь доклеивает этот пятачок сам: робот на нём стоит, значит он
свободен по построению. Пятачок намеренно МЕНЬШЕ корпуса и равен колёсному
прямоугольнику 0.636 x 0.711 м. Корпус 1.22 x 0.90 м свисает за колёса
примерно на 0.28 м спереди и сзади, и у кромки настила этот свес висит над
обрывом; объявить его свободным — ровно та ошибка, из-за которой робот и
уезжал за край.

После этой правки Nav2 доехал до цели с промахом 3 см и курсом -2.6° при
заданном нуле.


## Профиль рельсового ролика

Коллизия ролика набрана цилиндрами по измеренному профилю, см.
`RAIL_PROFILE` в `scripts/gen_robot_urdf.py`. Профиль снят с самого меша:

```bash
python3 - <<'PY'
import numpy as np, struct
b = open('src/maze_nav/meshes/wheel_hub_l.stl','rb').read()
n = struct.unpack('<I', b[80:84])[0]
rec = np.frombuffer(b, dtype=np.dtype([('n','<3f4'),('v','<3,3f4'),('a','<u2')]),
                    count=n, offset=84)
v = rec['v'].reshape(-1, 3).astype(float)      # меш в мм
y, r = v[:, 1], np.hypot(v[:, 0], v[:, 2])
for lo in np.arange(-124, -30, 1.5):
    m = (y >= lo) & (y < lo + 1.5)
    if m.sum() >= 4:
        print(f'{lo + 0.75:+7.1f}  {r[m].max():7.2f}')
PY
```

Получается: дорожка R=50 шириной 40 мм, галтель 51.8 → 54 → 57 → 60.6 →
64.8, реборда 75.

Раньше здесь была пара цилиндров — дорожка и реборда, — и реборда R=75
доходила до |y|=62.6, то есть наезжала на край трубы Ø51. Робот вставал на
рельсы на 11.9 мм выше расчётного, ехал заклиненным в прямом углу между
цилиндрами, а на перекосе всползал гребнем и сходил. Выглядело как
проблема конструкции, а было огрехом модели. Если заезд снова поведёт себя
странно — смотреть сюда первым делом.
