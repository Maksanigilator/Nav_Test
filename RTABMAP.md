# Утилиты RTAB-Map

Шпаргалка по тому, что приехало в образ вместе с `ros-jazzy-rtabmap-ros` 0.23.7.
Инструментов там под три десятка, названия непрозрачные, и без списка легко
не заметить готовое решение и написать своё.

Важно с самого начала: **RTAB-Map — это две разные вещи под одним именем.**

* **ROS 2-узлы** — то, из чего собирается навигация робота. Живут в пакетах
  `rtabmap_odom`, `rtabmap_slam`, `rtabmap_util`, `rtabmap_sync`, `rtabmap_viz`.
* **Standalone-утилиты** — отдельные программы `rtabmap-*`, которые работают
  с файлом базы `.db` или с датасетом на диске и про ROS ничего не знают.
  Ими считают метрики, чинят карты и гоняют офлайн-эксперименты.

Команды нашего проекта — в [RUN.md](RUN.md), тут только справочник.

## ROS 2-узлы

| Пакет | Узлы | Зачем |
|---|---|---|
| `rtabmap_odom` | `rgbd_odometry`, `stereo_odometry`, `icp_odometry` | одометрия: `odom→base`. Первый — по RGB-D, второй — по стереопаре, третий — по облакам/скану |
| `rtabmap_slam` | `rtabmap` | сам SLAM: карта, замыкания петли, `map→odom` |
| `rtabmap_viz` | `rtabmap_viz`, `rgbd_image_viewer` | живая визуализация: кадр с признаками, 3D-облако, замыкания |
| `rtabmap_sync` | `rgbd_sync`, `rgbdx_sync`, `stereo_sync`, `rgb_sync` | склейка RGB+depth+camera_info в одно сообщение `RGBDImage` |
| `rtabmap_util` | много, см. ниже | вспомогательные преобразования |

Полезное в `rtabmap_util`:

| Узел | Зачем |
|---|---|
| `obstacles_detection` | делит облако на «пол» и «препятствия» **по нормалям**, а не тупой отсечкой по высоте. Честнее работает на неровном полу и пандусах |
| `point_cloud_xyz`, `point_cloud_xyzrgb` | depth → облако точек |
| `pointcloud_to_depthimage` | обратное преобразование |
| `point_cloud_assembler`, `point_cloud_aggregator` | накопление облаков за несколько кадров |
| `imu_to_tf` | ориентация от IMU в TF |
| `map_assembler` | сборка глобальной карты из узлов |
| `disparity_to_depth` | диспаратность → глубина |
| `lidar_deskewing` | компенсация движения внутри развёртки лидара |
| `data_player` | проигрывание базы `.db` как источника данных |
| `rgbd_relay`, `rgbd_split` | пересылка и распаковка `RGBDImage` |

## Оценка результата

**`rtabmap-report`** — главный инструмент проверки. Считает ошибку траектории
против ground truth, записанного в базу.

```bash
rtabmap-report --loop /datasets/rtabmap_tum.db
```

Полезные ключи: `--loop` (ошибка на замыканиях), `--relative` (относительная
ошибка между позами), `--kitti` (метрика бенчмарка KITTI), `--scale` (подобрать
масштаб карты под эталон — нужно для монокулярных методов), `--latex` (таблица
для статьи), `--gt FILE.txt` (взять эталон из файла, а не из базы).

`--poses` выгружает три траектории в формате TUM RGB-D: `*_odom.txt` (одометрия),
`*_slam.txt` (оптимизированный граф), `*_gt.txt` (эталон). Их можно скормить `evo`.
Осторожно: файлы содержат строку заголовка `#timestamp ...` и **девятую колонку
`id`**, а `evo` требует ровно 8 полей без заголовка — надо срезать, см. [RUN.md](RUN.md).

**`rtabmap-info`** — сводка по базе без GUI: длина пройденного пути, время,
число узлов и слов, все параметры, с которыми делался прогон (изменённые
относительно дефолта помечены).

```bash
rtabmap-info /datasets/rtabmap_tum.db
```

## Разбор базы глазами: `rtabmap-databaseViewer`

Это **отладчик, а не плеер**. Нужен, когда что-то не сошлось и надо понять почему.
Чтобы просто посмотреть, как работает SLAM, запускай живую визуализацию
(`rtabmap_viz`, см. [RUN.md](RUN.md)).

```bash
xhost +local:docker
./run.sh rtabmap-databaseViewer /datasets/rtabmap_tum.db
```

**Первым делом — `View -> Concise Layout`.** По умолчанию окно открывает разом
девять панелей (`Constraints view`, `Graph view`, `3D view`, `Occupancy Grid`,
`Statistics`, `Info`, `Stereo view`, `Core Parameters`, `GUI Parameters`),
и в этой каше разобраться невозможно. В меню `View` вообще только две раскладки.

| Задача | Где |
|---|---|
| Полистать кадры | Две панели в центре (A и B), слайдеры под ними |
| **Посмотреть замыкания петли** | Панель `Constraints view`: выбор типа связи и перебор найденных. Для каждой — два кадра с сопоставленными признаками |
| Траектория и граф | Панель `Graph view` |
| **Облако всей сцены** | `Edit -> View 3D map...` — именно в `Edit`, не в `View` |
| Выгрузить траектории | `File -> Export poses...`: Raw, RGBD-SLAM, KITTI, TORO, g2o, KML |

По правому клику на панелях прячется ещё много опций — так устроен весь инструмент.

Что ещё умеет меню `Edit`: `Detect more loop closures...`, `Refine links...`,
`Merge components...`, `Regenerate local grid maps...`, `Edit depth image...`,
`Generate graph (*.dot)`.

## Экспорт карты

**`rtabmap-export`** достаёт из базы облака, меши и траектории.

```bash
rtabmap-export --cloud --output_dir /datasets /datasets/rtabmap_tum.db
```

Обязательно указать явно, что экспортировать — раньше `--cloud` подразумевался
по умолчанию, теперь нет. Варианты: `--cloud`, `--mesh`, `--poses`,
`--poses_camera`, `--poses_scan`, `--poses_gt`, `--images`, `--gps`.
Формат по умолчанию PLY, `--las` даёт LAS, `--ascii` — текстовый PLY.

## Офлайновые прогоны датасетов

Гоняют весь пайплайн по папке с данными **без ROS вообще** и сразу кладут
результат в базу. Быстрый способ проверить настройки, не поднимая узлы.

| Утилита | Датасет |
|---|---|
| `rtabmap-rgbd_dataset` | TUM RGB-D (папка с `rgb_sync`/`depth_sync` и `groundtruth.txt`) |
| `rtabmap-kitti_dataset` | KITTI odometry (стерео + Velodyne) |
| `rtabmap-euroc_dataset` | EuRoC MAV (стерео + IMU) |
| `rtabmap-cidsims_dataset` | CID-SIMS (RGB-D + IMU + колёсная одометрия) |

Заметка на будущее: **`rtabmap-rgbd_dataset` — альтернативный путь для нашего
этапа 1.** Он берёт исходную папку TUM (не bag) и не требует ни конвертации,
ни ROS. Мы пошли через ROS 2 bag сознательно: так проверяется не только сам
алгоритм, но и весь граф узлов, топиков и TF — то, что переезжает в симулятор.

## Доработка готовой карты

| Утилита | Что делает |
|---|---|
| `rtabmap-detectMoreLoopClosures` | ищет дополнительные замыкания в уже готовой базе. Ключи: `-r` радиус кластера, `-i` итерации, `--intra`/`--inter` (внутри одной сессии или между сессиями) |
| `rtabmap-globalBundleAdjustment` | глобальное уточнение всех поз и точек разом |
| `rtabmap-reduceGraph` | прореживает граф, сливая близкие узлы. Для больших карт |
| `rtabmap-cleanupLocalGrids` | вычищает из локальных сеток занятости то, что глобальная карта считает свободным. Убирает «призраков» от динамических препятствий, чтобы они не всплыли при повторном использовании карты |
| `rtabmap-reprocess` | прогоняет базу заново с другими параметрами, в том числе склеивает несколько баз. Им же обновляют формат старой базы |
| `rtabmap-recovery` | чинит повреждённую базу (например, после падения питания) |

`rtabmap-reprocess` особенно полезен: можно записать данные один раз и потом
крутить параметры сколько угодно, не выезжая на робота.

## Работа с камерами напрямую (без ROS)

Нужны редко — в ROS-стеке эту роль играет `realsense2_camera`.

| Утилита | Что делает |
|---|---|
| `rtabmap-calibration` | калибровка камеры |
| `rtabmap-camera` | захват с USB-камеры, папки картинок или видеофайла |
| `rtabmap-rgbd_camera` | захват с RGB-D камеры по драйверу (OpenNI, Freenect, RealSense2) |
| `rtabmap-dataRecorder` | запись потока с камеры прямо в базу `.db` |
| `rtabmap-odometryViewer` | GUI одометрии с живой камеры |
| `rtabmap-lidar_viewer` | просмотр потока с Velodyne по сети |

## Прочее

* **`rtabmap`** — полноценное GUI-приложение RTAB-Map (не ROS-узел). Умеет всё
  то же само по себе. `rtabmap --params` печатает **все** параметры с описаниями
  и значениями по умолчанию — самый быстрый способ узнать, что вообще можно крутить;
* **`rtabmap-console`** — тот же движок без GUI, для пакетной обработки папок
  с картинками или видео;
* `rtabmap-extractObject`, `rtabmap-res_tool` — служебные, нам не нужны.

## Грабли

* **GUI-утилиты не запускаются headless.** `rtabmap-databaseViewer`, `rtabmap`,
  `rtabmap-odometryViewer` требуют X11. `xhost +local:docker` на хосте,
  дальше `./run.sh <утилита>` — проброс дисплея в `run.sh` уже настроен.
* **`rtabmap-report` тоже собран с Qt**, хотя печатает только текст. В образе
  выставлен `QT_QPA_PLATFORM=xcb`, поэтому без дисплея он падает с
  «could not connect to display». Лечится переопределением:

  ```bash
  ./run.sh env QT_QPA_PLATFORM=offscreen rtabmap-report --loop /datasets/rtabmap_tum.db
  ```

* **`--help` у многих утилит показывает не их собственную справку**, а общую
  шапку параметров RTAB-Map. Собственный usage они печатают при запуске
  **без аргументов**. Если в выводе только «RTAB-Map options / Logger options» —
  запусти утилиту голой.
* **Параметры RTAB-Map задаются строками**, даже числовые: `'Reg/Force3DoF': 'true'`,
  `'Odom/ResetCountdown': '15'`. Это требование самой библиотеки, она парсит их
  своим конфигом, а не через rclcpp. Число или bool вместо строки — ошибка при старте.

## Записи с реальной RealSense (`.bag` от librealsense)

Это **не** ROS-бэг, хотя расширение то же и внутри формат ROS 1 bag. Пишет их
`realsense-viewer` и скрипты на `pyrealsense2`, а структура внутри своя:
`/device_0/sensor_0/Depth_0/image/data`, `/device_0/sensor_1/Color_0/image/data`,
плюс топики с настройками камеры (`Emitter_Enabled`, `Depth_Units`, `Laser_Power`…).
Проиграть такое через `ros2 bag play` нельзя.

Зато конвертировать не нужно: **`realsense2_camera` открывает такой файл как
виртуальное устройство** и публикует ровно те же топики, что живая камера.

```bash
ros2 launch maze_nav rtabmap_realsense_bag.launch.py bag:=/data/запись.bag viz:=true
```

Посмотреть, что внутри записи, до запуска (модель камеры, потоки, разрешения):
см. `rosbags.rosbag1.Reader` — скрипты в истории проекта, либо `rs-convert` из
`librealsense2-utils` на хосте.

### Выравнивание depth убивает скорость на CPU

Измерено на записи D435 (depth 848x480, color 640x480) в этом образе:

| Настройка | color | aligned depth |
|---|---|---|
| `align_depth.enable:=false` | 28.1 Гц | — |
| `align_depth.enable:=true` | **1.2 Гц** | **0.9 Гц** |

Падение в 30 раз. Последствие не «медленно», а «не работает»: узел камеры
не успевает за проигрыванием и **теряет кадры**, между обработанными кадрами
набегает по два метра движения, и визуальная одометрия перестаёт сходиться —
в логе `Not enough inliers 0/20 (matches=97)` при живых сопоставлениях.

Само по себе выравнивание нужно: у D435 depth и color имеют разные разрешения,
разные интринсики и физически разнесённые объективы, а RTAB-Map считает, что
пиксель (u,v) в обоих кадрах — одна точка сцены.

Варианты обхода:

* `accelerate_gpu_with_glsl:=true` — выравнивание на GPU (контейнер должен быть
  запущен с `--gpus all` и `NVIDIA_DRIVER_CAPABILITIES=all`);
* **писать в запись инфракрасный поток.** Depth у D400 вычисляется из пары ИК-камер,
  поэтому он **уже выровнен с `infra1`** — выравнивать нечего. Это путь из
  официального примера `rtabmap_examples/launch/realsense_d435i_infra.launch.py`.
  Но учти: там же отключается ИК-проектор (`depth_module.emitter_enabled: 0`),
  потому что его точечный узор статичен относительно камеры и даёт ложные
  «признаки», не движущиеся между кадрами. Для уже сделанной записи это
  не исправить — решать надо до съёмки;
* писать сразу выровненный поток при записи, а не при воспроизведении.

**Вывод на будущее: при записи данных с робота включай `infra1`+`infra2`**, даже
если кажется, что нужны только color и depth. Без них запись нельзя прогнать
через визуальную одометрию на полной скорости.
