# ROS 2 Jazzy + Nav2 + Gazebo Harmonic

1. Сборка

cd ~/Nav_Test
docker build -f docker/Dockerfile -t nav2:jazzy .
часть	смысл
-f docker/Dockerfile	где лежит Dockerfile
.	контекст сборки — от него считается путь в COPY docker/entrypoint.sh
-t nav2:jazzy	имя и тег образа
Именно поэтому запускать надо из Nav_Test/, а не из docker/ — иначе COPY не найдёт файл.

⏱ Первый раз — минут десять: 1.2 ГБ базы плюс Nav2 со всеми зависимостями. Дальше пересборки будут быстрыми за счёт кэша слоёв.

2. Запуск

Проще всего — ./run.sh: он же подключается вторым терминалом к уже поднятому контейнеру.
Полный эквивалент вручную:

docker run -it --rm \
  --name nav2 \
  --network host \
  --ipc host \
  --gpus all \
  -e DISPLAY="$DISPLAY" \
  -e XAUTHORITY=/tmp/.docker.xauth \
  -e NVIDIA_DRIVER_CAPABILITIES=all \
  -e GZ_SIM_RESOURCE_PATH=/opt/ros/jazzy/share/turtlebot3_gazebo/models:/root/ros_ws/src/maze_nav/models \
  -v "$XAUTHORITY":/tmp/.docker.xauth:ro \
  -v /tmp/.X11-unix:/tmp/.X11-unix:rw \
  --device /dev/dri:/dev/dri \
  -v ~/Nav_Test/src:/root/ros_ws/src \
  nav2:jazzy
Разбор флагов
флаг	зачем
--network host	DDS discovery работает без настройки; без этого узлы не найдут друг друга
--ipc host	разделяемая память для DDS. Без него /dev/shm = 64 МБ, и большие топики (карты, облака точек) молча теряются
--gpus all	доступ к RTX 3080
-e NVIDIA_DRIVER_CAPABILITIES=all	критично: без него дадут CUDA, но не OpenGL, и Gazebo откроется чёрным окном
-e GZ_SIM_RESOURCE_PATH	где gz sim ищет модели и миры. Заменяет пару GAZEBO_MODEL_PATH/GAZEBO_RESOURCE_PATH из Gazebo Classic
-v "$XAUTHORITY":/tmp/.docker.xauth:ro	X11-cookie. У тебя он в /run/user/1000/gdm/, а не в ~/.Xauthority — рецепты из интернета тут не сработают
-v /tmp/.X11-unix	сокет X-сервера
--device /dev/dri	прямой рендеринг
-v ~/Nav_Test/src:...	твой код с хоста внутрь контейнера
--rm	удалить контейнер при выходе
Про --rm: контейнер исчезает, когда закроешь этот терминал. Всё, что ты доставил внутрь руками, пропадёт — но src/ смонтирован с хоста и сохранится. Это нормальный режим для разработки. Если захочешь, чтобы контейнер жил дольше, убери --rm и добавь -d.

3. Симулятор

ros2 launch maze_nav maze.launch.py            # лабиринт maze1 + TurtleBot3
ros2 launch maze_nav maze.launch.py gui:=false # без окна, только физика

4. Чем Jazzy отличается от Humble

Gazebo Classic 11 в Jazzy нет вообще: он EOL и не собирается под Ubuntu 24.04.
Симулятор здесь — Gazebo Harmonic (команда gz sim), а связь с ROS даёт ros_gz_bridge
вместо плагинов libgazebo_ros_*. Что из этого следует на практике:

старое (Humble)	новое (Jazzy)
gzserver / gzclient	gz sim -s / gz sim -g (через ros_gz_sim/gz_sim.launch.py)
пакет gazebo_ros	пакеты ros_gz_sim, ros_gz_bridge
GAZEBO_MODEL_PATH + GAZEBO_RESOURCE_PATH	один GZ_SIM_RESOURCE_PATH
кэш в ~/.gazebo	кэш в ~/.gz
model://ground_plane из базы моделей	земля и солнце описаны прямо в .world (иначе gz полез бы в онлайновую Fuel)
.world в формате SDF 1.6	SDF 1.10 + системные плагины Physics/SceneBroadcaster/Sensors/Imu внутри мира

Геометрия лабиринта при переезде не менялась — maze1.world перегенерирован тем же
seed (gen_maze.py --cells 6 --seed 1), так что карта maps/maze1.pgm остаётся валидной.

5. Грабли перехода Humble -> Jazzy в конфигах Nav2

Их стоит знать, если будешь править params руками:

* имена плагинов только через "::". Форма nav2_navfn_planner/NavfnPlanner
  в Jazzy не существует, planner_server падает в FATAL и обрывает весь bringup;
* collision_monitor теперь входит в nav2_bringup по умолчанию и без своей
  секции параметров валит запуск на "observation_sources is not initialized";
* behavior_server больше не знает costmap_topic/footprint_topic — вместо них
  local_costmap_topic, global_costmap_topic, local_footprint_topic,
  global_footprint_topic, а фреймов стало два: local_frame и global_frame.

# 6. Навигация по RGB-D вместо лидара (ветка rgbd-nav)

Дорожная карта работ и состояние этапов — в [PLAN.md](PLAN.md),
команды запуска — в [RUN.md](RUN.md), справочник по утилитам
RTAB-Map — в [RTABMAP.md](RTABMAP.md).

Следующий робот лидара не имеет вообще — только RealSense **D435** и внешний IMU
(своего IMU у D435 нет, он есть только у D435i).
Это не замена одного топика: лидар закрывал сразу две подсистемы, и обе надо
заменить по отдельности.

| Подсистема | Было | Стало |
|---|---|---|
| одометрия, `odom→base` | энкодеры колёс | визуальная одометрия `rtabmap_odom` (+IMU, +EKF) |
| локализация, `map→odom` | AMCL по `/scan` | `rtabmap_slam` — он же отдаёт `/map` |
| препятствия | LaserScan-слои костмапов | `PointCloud2` в STVL |

Nav2 при этом не меняется вообще: планировщики, контроллеры и BT работают как есть,
меняются только поставщики данных.

## Что важно знать про D435

Модель определена по метаданным реальной записи (`Intel RealSense D435`,
серийник 147322070391). В плане изначально значился D415 — это была ошибка,
и разница существенная:

| Параметр | D435 (наш) | D415 (как думали) |
|---|---|---|
| FOV depth | **87°×58°** | 65°×40° |
| Затвор ИК/depth | **глобальный** | роллинг |
| Затвор RGB | роллинг | роллинг |
| Min-Z | **~0.28 м** | ~0.45 м |
| IMU | нет (есть у D435i) | нет |

Состав устройства в записи — два сенсора, Stereo Module и RGB Camera;
Motion Module отсутствует, то есть это обычный D435 **без IMU**.

Отсюда решения:

* **внешний IMU обязателен**, а не «желателен»: без него у RTAB-Map нет ни приора
  на поворот, ни выравнивания по гравитации;
* **одометрию строить по ИК-потоку, а не по RGB.** У D435 ИК-сенсоры глобальные,
  цветная камера роллинговая. На реальной записи 91% цветных кадров оказались
  смазаны — по ИК при том же движении смаза будет принципиально меньше. Бонусом
  глубина уже выровнена с `infra1`, и выравнивание, роняющее поток до 1 Гц,
  просто не нужно;
* **выдержку фиксировать вручную**: смаз зависит от времени экспозиции, а не
  от частоты кадров. Замеры показали, что 30 Гц дают комфортные 7.5 пикселя
  смещения между кадрами — частота ни при чём, а автоэкспозиция в полутьме
  задирает выдержку до 30+ мс;
* **работаем на 848×480**, а не 1280×720: меньше время развёртки строки и трафик;
* FOV 87° заметно легче, чем предполагавшиеся 65°, но **затухание препятствий**
  в костмапе (`voxel_decay` у STVL) всё равно обязательно: камера смотрит вперёд,
  и без памяти препятствие сбоку исчезает ровно тогда, когда робот начинает поворот.

## Заметка: почему в симуляторе моделируется цветной тракт, а не ИК

Решение принято осознанно, и у него есть цена — записываю, чтобы потом
не пересматривать вслепую.

**Развилка.** У D435 два возможных входа для визуальной одометрии:

| Тракт | FOV | Затвор | Выравнивание глубины |
|---|---|---|---|
| Цветной (RGB) | **69.4° x 42.5°** | роллинг | нужно, depth -> color |
| Инфракрасный (`infra1`) | **87° x 58°** | глобальный | не нужно, глубина уже в этом кадре |

По технике ИК-тракт лучше по всем трём пунктам. Но картинка в нём серая,
а значит **не будет цветной 3D-карты**.

**Что выбрано.** Цветной тракт, FOV 69.4°, один сенсор `rgbd_camera`.
Причины:

1. цветная карта нужна как результат, её хотелось видеть;
2. **в симуляторе выравнивание бесплатно.** Проблема, которая уронила поток
   с 28 Гц до 1.2 на реальной записи, — это librealsense, жгущий CPU при
   пересчёте глубины в кадр цветной камеры. В Gazebo цвет и глубина рождаются
   из одной виртуальной оптики и совмещены по построению. То есть главный
   довод против RGB в симуляторе не действует;
3. смаз от роллингового затвора в Gazebo тоже не моделируется, так что второй
   довод против RGB здесь не проявится.

**Чем платим.** Обзор для костмапа 69° вместо 87°, то есть примерно на четверть
меньше углового поля по горизонтали. Слепые зоны по бокам будут шире, чем
на реальном ИК-тракте, — симулятор в этом месте пессимистичен, и это безопасная
сторона ошибки.

**Чего симулятор при таком выборе НЕ проверит.** Ровно те две вещи, ради которых
ИК-тракт и нужен: смаз от роллингового затвора и стоимость выравнивания.
Обе проявятся только на железе, и обе уже описаны в разделе про D435.
Если на роботе решим идти по ИК, модель камеры в симуляторе надо будет
переставить на 87° и переименовать фрейм.

## Что добавлено в образ

Отдельный слой в [Dockerfile](docker/Dockerfile), чтобы правки в нём не роняли кэш
всего Nav2 выше. Все пакеты ставятся бинарниками под Jazzy, собирать из исходников
ничего не нужно: `rtabmap-ros`, `realsense2-camera`, `spatio-temporal-voxel-layer`,
`depth-image-proc`, `robot-localization`, `imu-filter-madgwick`,
`image-transport-plugins`, `pointcloud-to-laserscan`, плюс `rosbags` и `evo` из pip.

Грабли, на которые уже наступили:

* в базовом образе `osrf/ros:jazzy-desktop` **нет `pip3`** — нужен `python3-pip`;
* класс STVL регистрируется как **`spatio_temporal_voxel_layer/SpatioTemporalVoxelLayer`** — через слэш.
  pluginlib берёт ключом атрибут `name` из plugins.xml, а не `type`;
  правило «в Jazzy только через `::`» действует лишь для плагинов самого
  Nav2, у которых `name` не объявлен. Неверное имя роняет bringup в FATAL;
* `/datasets` монтируется в корень, а не в `/root/datasets`: под `--user` контейнер
  не видит `/root` (права 700), а датасеты удобнее держать с правами хоста.

## Этап 1: опорная точка на датасете TUM RGB-D

Прежде чем лезть в симулятор, RTAB-Map проверен на данных с ground truth —
иначе нельзя отличить «алгоритм настроен неверно» от «мир/камера плохие».
Команды — в [RUN.md](RUN.md), результат: **ATE RMSE 2.0 см на 20 м, 16 замыканий петли**,
против 5.9 см у чистой одометрии.

### Почему свой конвертер бэга

Штатный рецепт из `rtabmap_examples/launch/rgbdslam_datasets.launch.py` требует
установленного ROS 1: `rosbag decompress`, `roscore` и два ROS1-скрипта.
Вместо этого — [scripts/tum_bag_to_ros2.py](src/maze_nav/scripts/tum_bag_to_ros2.py),
работающий в два прохода:

1. **`rosbags.convert`** переводит ROS 1 → ROS 2. Своими руками это делать нельзя:
   у сообщений реально разные поля. У `CameraInfo` матрицы назывались `D/K/R/P`,
   а в ROS 2 они `d/k/r/p`; у `Header` исчез `seq`; тип `tf/tfMessage` заменён на
   `tf2_msgs/TFMessage`. Библиотека знает все такие различия.
2. **Правка фреймов** уже внутри ROS 2, где чтение и запись идут одним типовым
   хранилищем. Делается ровно то, ради чего в оригинале нужны ROS1-скрипты:
   снимается ведущий `/` с имён фреймов (ROS 2 такие отвергает) и потомки фрейма
   `world` в `/tf` переименовываются в `<имя>_gt`. Без второго ground truth
   публиковал бы `world→kinect`, визуальная одометрия — `odom→kinect`,
   и два родителя у одного фрейма ломали бы дерево TF.

### Почему выключена статика kinect → openni_rgb_optical_frame

Штатный пример RTAB-Map её публикует с комментарием «/tf topic is missing in the
converted ROS2 bag». Это верно для **их** способа конвертации. Наш конвертер `/tf`
сохраняет полностью — в бэге живёт цепочка
`kinect → openni_camera → openni_rgb_frame → openni_rgb_optical_frame`,
публикуемая на 10 Гц весь прогон. Если поверх неё поднять ещё и прямую связь
`kinect → openni_rgb_optical_frame`, у фрейма окажется два родителя и дерево
развалится. Поэтому в [rtabmap_tum.launch.py](src/maze_nav/launch/rtabmap_tum.launch.py)
это вынесено в аргумент `publish_camera_tf`, по умолчанию выключенный.
