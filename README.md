# Nav_Test — базовая ветка

Это базовая ветка для проектов на ROS 2 Jazzy. В ней собрано окружение в
докере, навигация Nav2 по лидару и симулятор с лабиринтами — то, от чего
отталкиваются прикладные работы. Сама по себе она ничего не решает: это
стенд, на котором проверяется, что навигация едет.

Всё работает внутри контейнера. На хосте нужны только docker и git — ROS,
Gazebo и Nav2 на машину не ставятся.

## Ветки

Три ветки идут слоями, каждая следующая содержит предыдущую целиком:

| ветка | что добавляет |
|---|---|
| `main` | окружение, Nav2 по лидару, симулятор с лабиринтами |
| `rgbd-nav` | поверх `main`: RTAB-Map и RealSense — навигация по RGB-D без лидара |
| `agrobot` | поверх `rgbd-nav`: реальный агроробот, заезд на рельсы и съезд |

Общие правки — окружение, `run.sh`, базовые конфиги Nav2 — делаются здесь, в
`main`, и поднимаются вверх слияниями. Вниз не сливается ничего: иначе чистка
нижнего слоя выпотрошила бы верхний.

`RTK-GOROD` стоит отдельно и на `main` не основана — это материалы своей
задачи: граф маршрута, регламент и прошивка контроллера.

## Быстрый старт

```bash
git clone <репозиторий> && cd Nav_Test
docker build -f docker/Dockerfile -t nav2:jazzy .    # первый раз ~10 минут
```

Собирать обязательно из корня проекта, а не из `docker/`: контекст сборки —
это `.`, от него считается путь в `COPY docker/entrypoint.sh`.

Дальше два терминала:

```bash
./run.sh ros2 launch maze_nav maze.launch.py         # лабиринт и TurtleBot3

./run.sh ros2 launch nav2_bringup bringup_launch.py use_sim_time:=true \
    map:=/root/ros_ws/src/maze_nav/maps/maze1.yaml \
    params_file:=/root/ros_ws/src/maze_nav/params/maze_params.yaml
```

И третий, если нужен RViz с панелями Nav2:

```bash
./run.sh ros2 launch nav2_bringup rviz_launch.py
```

Цель ставится кнопкой **2D Goal Pose**. Начальную позу подсказывать не нужно:
карта снята с того же мира, и AMCL сходится сам.

Остальные команды — генерация лабиринта, съём карты, замер сектора лидара —
в [RUN.md](RUN.md).

## Как работает `./run.sh`

Это единственная точка входа. Первый вызов поднимает контейнер, каждый
следующий **подключается к уже работающему**, а не запускает второй:

```bash
./run.sh                    # первый терминал — поднять контейнер
./run.sh                    # второй и третий — зайти в тот же самый
./run.sh ros2 topic list    # выполнить разовую команду и выйти
```

Контейнер запускается с `--rm` и исчезает, когда закроешь первый терминал.
Это нормальный режим для разработки: код лежит на хосте и смонтирован внутрь,
а артефакты сборки живут в именованных томах `nav2_build` и `nav2_install` и
переживают перезапуск. Поэтому пересобирать `colcon` после каждого старта не
нужно.

Корень проекта определяется по пути самого скрипта, а не по `$HOME` — клон в
любой каталог работает одинаково.

### Пользователь и разделяемая память

Самое неочевидное место. Контейнер запускается **под тем же пользователем,
что и хост**:

```bash
--ipc host
--user "$(id -u):$(id -g)"
-e HOME=/root
```

Зачем это нужно. ROS 2 в Jazzy по умолчанию говорит через Fast DDS, а тот
доставляет большие сообщения не по сети, а через разделяемую память — записью
в файлы в `/dev/shm`. Файлы создаются с правами `0644` и владельцем-создателем.
Отсюда два следствия:

* без `--ipc host` у контейнера **свой** `/dev/shm` на 64 МБ, и разделяемая
  память между ним и хостом не заработает ни при каких правах;
* при разных пользователях файлы сегмента чужие, и доставка запрещена правами.

Второй случай коварен тем, как он выглядит снаружи: `ros2 node list` и
`ros2 topic list` показывают всё, граф построен, подписки есть — а данные не
приходят. Ни ошибки, ни предупреждения.

Из `--user` вытекает и остальное: под ним докер не подставляет `HOME`, поэтому
он задан явно, а `/root` в образе открыт на запись — иначе оболочка не нашла
бы ни `.zshrc`, ни настроек ROS.

Размер сегмента по умолчанию около 512 КБ, и кадр камеры 848×480 в него не
влезает. Поэтому подключается [fastdds_profiles.xml](fastdds_profiles.xml) —
он поднимает сегмент до 64 МБ.

### Если что-то пошло не так

**Узлы и топики видны, данных нет.** Почти наверняка разделяемая память. Для
проверки принудительно переключись на UDP:

```bash
FASTDDS_BUILTIN_TRANSPORTS=UDPv4 ./run.sh
```

Если так данные пошли — дело в `/dev/shm`. Смотреть надо на UID: `id -u` на
хосте и `id -u` внутри контейнера должны совпадать. UDP при этом остаётся
рабочим запасным вариантом, просто медленнее на тяжёлых потоках.

**Два источника `odom` и разорванное дерево TF** при свободных процессоре и
видеокарте. Это две сессии в одном домене DDS: при `--network host` они видят
узлы друг друга и склеиваются в один ROS-граф, даже если это разные
контейнеры. Вторую поднимать в своём домене:

```bash
ROS_DOMAIN_ID=43 ./run.sh
```

Имя контейнера тогда тоже меняется, и они не конфликтуют.

**`executable file not found`** на команду, которая в образе точно есть.
`docker exec` не проходит через точку входа, и ROS не попадает в `PATH`.
`run.sh` это уже обходит, запуская команду через интерактивный `zsh`, —
ошибка означает, что команду запустили мимо него.

**Окно RViz или Gazebo не открывается.** Смотри следующий раздел.

### Видеокарта NVIDIA

Когда карта есть, `run.sh` передаёт три вещи:

```bash
--gpus all
-e NVIDIA_DRIVER_CAPABILITIES=all
-e __NV_PRIME_RENDER_OFFLOAD=1 -e __GLX_VENDOR_LIBRARY_NAME=nvidia
```

Первое даёт контейнеру доступ к карте. Второе критично и его часто забывают:
без него дадут CUDA, но **не OpenGL**, и Gazebo откроется чёрным окном. Третье
уводит рендеринг на NVIDIA — иначе RViz садится на встроенную Intel и идёт
единицы кадров в секунду.

На хосте для этого нужен `nvidia-container-toolkit`. Проверить, что он
работает:

```bash
nvidia-smi                                        # на хосте
./run.sh glxinfo | grep "OpenGL renderer"         # в контейнере
```

Вторая команда должна назвать NVIDIA. Если там Mesa или llvmpipe — рендеринг
идёт программно, и тяжёлая трёхмерная сцена будет ползти.

### Если видеокарты нет

```bash
./run_no_nvidia.sh
```

Тот же `run.sh`, только с выставленным `NO_NVIDIA=1`: не передаётся
`--gpus all`, не задаются переменные NVIDIA, OpenGL идёт через Mesa и
`/dev/dri`. Для RViz и Gazebo встроенной видеокарты хватает, доустанавливать
ничего не нужно.

Отдельный файл, а не автоопределение — сделано нарочно. Докер отвечает
`could not select device driver` и когда карты нет вовсе, и когда она есть, но
не подхватилась; по сообщению эти случаи не различить. Из имени команды сразу
видно, что запущено.

Передавать `--gpus all` безусловно нельзя: на машине без NVIDIA контейнер не
стартует вообще.

### Окно: X11 или браузер

Если `DISPLAY` задан, окна идут на твой экран обычным X11. Файл cookie под GDM
лежит в `/run/user/1000/gdm/Xauthority`, а не в `~/.Xauthority` — рецепты из
интернета тут не срабатывают, `run.sh` берёт правильный путь сам.

По SSH достаточно подключиться с `ssh -X`, и окна поедут на локальную машину.

Если `DISPLAY` пуст — а так бывает в SSH без `-X` и в некоторых терминалах
редакторов — `run.sh` поднимает виртуальный экран `:99` и noVNC. RViz тогда
открывается в браузере:

```
http://localhost:6080
```

На виртуальном экране рендеринг всегда программный: привязать драйвер NVIDIA
там не к чему, и с ним окно получается чёрным.

| путь | что это |

| `run.sh`, `run_no_nvidia.sh` | запуск контейнера |
| `fastdds_profiles.xml` | транспорт Fast DDS, размер сегмента памяти |
| `src/maze_nav/launch/` | `maze.launch.py` — мир и робот |
| `src/maze_nav/worlds/`, `maps/` | лабиринт и снятая с него карта |
| `src/maze_nav/params/` | три набора параметров Nav2 |
| `src/maze_nav/scripts/` | генератор лабиринтов и вспомогательные узлы |

## Три набора параметров Nav2

Отличаются локальным планировщиком и настройкой AMCL:

| файл | планировщик | зачем |
|---|---|---|
| `maze_params.yaml` | `dwb_core::DWBLocalPlanner` | основной: выборка траекторий, аккуратен в узких коридорах |
| `maze_params_rpp.yaml` | RotationShim + RegulatedPurePursuit | ведёт по пути, а не перебирает траектории; разворот на месте при отклонении больше 34° |
| `maze_params_fov180.yaml` | то же, что `rpp` | плюс AMCL под урезанный сектор лидара: 90 лучей вместо 60, частиц 1000–3000, порог обновления 0.15 м |

Последний нужен, когда часть лучей перекрыта конструкцией робота: с
настройками по умолчанию AMCL в такой ситуации расходится. Фактический сектор
обзора меряется скриптом `scan_fov.py` — он считает, как часто каждый угол
возвращает корректную дальность.

## Грабли конфигов Nav2

Их стоит знать, если будешь править `params/` руками:

* **имена плагинов только через `::`.** Форма `nav2_navfn_planner/NavfnPlanner`
  в Jazzy не существует: `planner_server` падает в FATAL и обрывает весь
  bringup;
* **`collision_monitor`** входит в `nav2_bringup` по умолчанию и без своей
  секции параметров валит запуск на `observation_sources is not initialized`;
* **`behavior_server`** больше не знает `costmap_topic` и `footprint_topic` —
  вместо них `local_costmap_topic`, `global_costmap_topic`,
  `local_footprint_topic`, `global_footprint_topic`. Фреймов стало два:
  `local_frame` и `global_frame`.

Симулятор здесь Gazebo Harmonic (`gz sim`), связь с ROS даёт `ros_gz_bridge`.
Модели и миры ищутся по одному пути `GZ_SIM_RESOURCE_PATH`, земля и солнце
описаны прямо в `.world` — иначе Gazebo полез бы за ними в онлайновую Fuel.
