# Контейнер с YOLO: детектор знаков по запросу

Второй контейнер рядом с `nav2:jazzy`. Нужен потому, что в образе с Nav2
нет torch, а качать его несколько гигабайт по Wi-Fi долго и ненадёжно —
две сборки подряд обрывались по таймауту. В образе `yolo:latest` torch с
CUDA и ultralytics уже стоят.

Контейнеры общаются обычными средствами ROS 2: оба идут с `--network host`,
одинаковым `ROS_DOMAIN_ID=42` и `rmw_fastrtps_cpp`, поэтому сервис и топики
видны с обеих сторон без всякой настройки.

```
Raspberry (ffmpeg :8080)          контейнер yolo:latest         контейнер nav2:jazzy
         │                                  │                            │
         │   ◄── HTTP только в момент ──────┤                            │
         │       запроса, 5 кадров          │                            │
         │                                  │  /detect_signs ◄───────────┤
         │                                  │  (std_srvs/Trigger)        │
         │                                  ├── /sign_detected ─────────►│
         │                                  │   std_msgs/String          │
```

## Откуда взялись файлы

`docker/Dockerfile`, `docker/entrypoint.sh`, `requirements.txt` и
`docker-compose.yml` — **побайтные копии** из проекта
`~/roshack/Roshack-yolodocker`, которым собран образ `yolo:latest`.
Они лежат здесь только для справки и воспроизводимости; исходный проект
не менялся. Образ пересобирать не нужно, он уже есть на машине.

`nodes/sign_detector.py` — новое, написано под эту задачу.

Модель берётся из `src/yolo/dataset_v3_180.pt`, второй копии нет:
`run_yolo.sh` монтирует репозиторий целиком.

## Запуск

```bash
./run_yolo.sh                       # поднять контейнер
# внутри:
python3 /root/ros_ws/src/yolo/sign_detector.py --ros-args \
    -p stream_url:=http://<IP робота>:8080/stream \
    -p device:=cuda:0
```

Запрос — из любого контейнера того же домена, в том числе из `nav2`:

```bash
ros2 service call /detect_signs std_srvs/srv/Trigger
```

Ответ выглядит так:

```
success=True, message='no_left (класс 4, уверенность 0.95, в 5 из 5 кадров, 0.54 с)'
```

## Почему по запросу, а не потоком

Пока сервис не вызван, к роботу не уходит ни одного байта. Канал у нас
общий с лидаром, TF и одометрией, и он уже подтверждён как узкое место:
из-за него пришлось снижать частоту EKF с 45 до 25 Гц. Постоянный
видеопоток добил бы его окончательно.

Обратная сторона: знак виден только в тот момент, когда его спросили.
Для схемы «приехали в точку — осмотрелись» этого достаточно.

## Параметры

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `source` | `snapshot` | `snapshot` — отдельные снимки по запросу; `stream` — кусок MJPEG-потока |
| `snapshot_url` | выводится из `stream_url` | адрес одиночного кадра |
| `snapshot_gap` | `0.25` | пауза между снимками, секунд |
| `stream_url` | `http://192.168.1.99:8080/stream` | MJPEG-поток робота (нужен только при `source:=stream`) |
| `model_path` | `/root/ros_ws/src/yolo/dataset_v3_180.pt` | веса |
| `device` | `cuda:0` | `cuda:0` или `cpu` |
| `conf` | `0.5` | порог уверенности |
| `imgsz` | `640` | вход сети, как при обучении |
| `burst` | `3` | сколько кадров брать за запрос |
| `timeout` | `5.0` | сколько ждать кадры, секунд |
| `service_name` | `/detect_signs` | имя сервиса |

Кадров берётся несколько: одиночный снимок легко ловит смаз или засветку,
а решение по нему меняет маршрут. Робот в этот момент стоит, полсекунды
роли не играют.

Каждый кадр запрашивается **отдельным коротким GET** — открылось
соединение, пришла картинка, закрылось. В промежутках к роботу не уходит
ничего. Прежний режим с открытием MJPEG-потока оказался хрупким: надо
было дождаться, пока накопится нужное число кадров на частоте камеры, и
на загруженном канале это регулярно кончалось `Read timed out` или
«успели взять 0 кадров из 5». Замер на живой камере: три снимка
укладываются в 1.5–2.8 с против 2.7–5.9 с у потокового режима.

Пауза `snapshot_gap` между снимками нужна потому, что камера отдаёт 5
кадров в секунду: три запроса подряд вернули бы одну и ту же картинку.

## Выход

| Топик | Тип | Что внутри |
|---|---|---|
| `/sign_detected` | `std_msgs/String` | имя знака для `apply_sign`, пустая строка — не нашли |
| `/sign_detections` | `std_msgs/String` | то же плюс JSON: классы, уверенность, рамки, число кадров |
| `/sign_image` | `sensor_msgs/Image` | кадр с нарисованными рамками |

Тот же кадр пишется файлом `src/yolo/last_detection.jpg` — он лежит в
примонтированном репозитории и открывается с хоста обычной смотрелкой,
поднимать RViz ради разовой проверки не нужно. Из пачки кадров берётся
тот, на котором детектор был увереннее всего: первый попавшийся не
годится, именно на нём знака может не оказаться.

Модель детекционная (`task: detect`), а не сегментационная — знаки
обводятся рамкой, масок по контуру не будет.

Имя точки графа сюда **не подставляется**. Где стоит робот, знает
`route_follower` — он и соберёт строку `«точка:знак»` для `/route_sign`.

## Классы модели

Модель `dataset_v3_180.pt` (YOLOv8n, 8 классов, вход 640) называет классы
цифрами, и они идут подряд по Приложению Б регламента. Проверено прогоном
по картинкам знаков из самого регламента — шесть из шести, уверенность
0.96–0.98:

| класс | знак | имя в графе |
|---|---|---|
| `1` | Б.1 движение прямо | `only_straight` |
| `2` | Б.2 движение налево | `only_left` |
| `3` | Б.3 движение направо | `only_right` |
| `4` | Б.4 поворот налево запрещён | `no_left` |
| `5` | Б.5 поворот направо запрещён | `no_right` |
| `6` | Б.6 место остановки | `stop` |
| `7` | Б.7 место стоянки | `parking` |
| `8` | Б.8 опасный объект | — маршрут не меняет |

## Чего ещё нет

На роботе нет камеры и ffmpeg — без них сервис вернёт
`поток недоступен`. Проверить сторону робота можно так:

```bash
ss -tlnp | grep 8080                                  # на Raspberry
curl -s --max-time 3 http://<IP>:8080/stream | head -c 100 | xxd | head -2
```
