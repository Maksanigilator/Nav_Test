# Этап 2: совмещение точки, направления рельсов и прямой проезд

Первоначально подготовлено без запуска на роботе. После отдельной команды
оператора пакеты собраны и серверы запущены в `nav2_vlad_0`; поиск выключен,
сервоуправление в IDLE, цели движения не отправлялись. Модуль `rail_visual_entry`
предоставляет отдельное действие `/rails/enter`. Он не стартует вместе
с поиском или после завершения подъезда. В состоянии ожидания не
публикует команды скорости.

## Настройки

`config/entry.yaml`:

- Целевая точка: `x=(width-1)/2`, `y=height-1-80`. Для 848×480 это
  `(423.5, 399)` — по центру, на 80 пикселей выше нижнего края.
- Дистанция прямого проезда: 1,5 м.
- Постоянная скорость прямого проезда: 0,12 м/с.
- Предельное время прямого проезда: ровно `2*distance/speed`, то есть
  25 секунд с этими значениями. Проверяется на каждом такте управления
  20 Гц по монотонным часам; паузы не продлевают срок.
- Допуск совмещения: ±12 пикселей по каждой координате и ±3° по
  направлению рельсов, три разных кадра и не менее 0,3 секунды
  устойчивого одновременного совмещения.
- Отдельный таймаут выравнивания: 60 секунд.

## ALIGN

Из маски и выровненной глубины общий геометрический детектор выделяет
согласованную тройку линий. Центр перемычки в её плоскости проецируется
обратно в исходное изображение; рядом с ним требуется валидная глубина
внутри маски. Карта и сохранённый реестр для этого этапа не нужны.

Регулятор использует две нормализованные координаты изображения и угол
продольной оси рельсов относительно `base_footprint`. Угол получается
из тех же видимых параллельных линий после исправления перспективы по
плоскости/TF. Это IBVS точки с дополнительным визуальным признаком курса:
сохранённый угол карты и одометрия не заменяют наблюдение линии.

Рассчитываются `vx`, `vy`, `wz` для омниколёс. Матрица 3×3 включает
боковое перемещение, глубину, TF камеры и плечо камеры при повороте;
для направленной оси рельсов производная угла равна `-wz`. Поворот
компенсируется перемещением, чтобы не уводить центр перемычки от цели.
Переход в DRIVE требует одновременно допуска точки и угла.
Разворот оси >60° отклоняется как несовместимый с заездом вперёд.

Пределы ALIGN: вперёд 0,16 м/с, назад 0,12 м/с, боком 0,14 м/с,
поворот 0,35 рад/с. Вне допуска минимумы ненулевых команд — 0,04 м/с
и 0,10 рад/с. Если покомпонентное повышение нарушает снижение общей
ошибки, используется общий масштаб. Ограничения ускорения: 0,35 м/с²
и 0,8 рад/с². Минимумы применяются до плавного нарастания команды,
поэтому первые такты могут быть меньше порога трогания. Внутри обоих
допусков и при потере наблюдения публикуется ноль без задержки разгона.
Эти минимумы требуют проверки на реальном приводе; масса сама по себе
не определяет порог трогания. Скорость DRIVE остаётся 0,12 м/с.

При отсутствии свежего достоверного наблюдения команды становятся
нулевыми. Через две секунды без наблюдения действие завершается ошибкой.
Плохо обусловленный якобиан, неподходящая маска, отсутствие трёх линий,
невалидная глубина или TF также не разрешают движение по старой оценке.

## DRIVE

После совмещения фиксируются положение и курс робота по `/odom`.
По умолчанию это визуальная локализация в `odom`, сообщение `Odometry`
для `base_footprint`. Система координат выбирается конфигом; здесь нужен
непрерывный источник положения, поэтому предпочтительнее локальный
`odom`, который не скачет при коррекции глобальной карты.

Продвижение — проекция текущего смещения на начальное направление:
`distance = dot(current_xy-start_xy, [cos(start_yaw), sin(start_yaw)])`.
Боковое смещение и движение назад не засчитываются как проезд вперёд.
До достижения 1,5 м публикуется `vx=0.12, vy=0, wz=0`.
На этом этапе сегментация не участвует в управлении и не выполняется
внутри этого модуля. Работа отдельного YOLO-узла не изменяется.

По достижении расстояния, таймауту, отмене, потере локализации,
скачку координат, смене системы координат или отклонению курса более
20° публикуется остановка. Курс контролируется только для прекращения
действия, не для коррекции движения. Завершение означает достижение
заданной дистанции по локализации, а не подтверждение механического
попадания колёс на рельсы.

Команды идут в `/cmd_nav_raw`, через существующий `cmd_sign` и аппаратный
мультиплексор. Узел не поднимает эти компоненты. Система должна уже
иметь рабочую цепочку команд и переключённый оператором режим управления.
Подъезд и заезд используют общий файловый lock внутри одного контейнера
и не могут выполняться одновременно. Lock не координирует посторонние
программы движения или процессы с отдельным `/tmp`.

## Команды (подготовлены; агент их не выполнял)

На хосте робота открыть отдельный контейнер новой копии в домене
работающего стека. Этот вызов запускает оболочку, не второй SLAM/Nav2:

```bash
cd ~/projects/aida_nav_vlad/Nav_Test
ROS_DOMAIN_ID=0 ./run.sh bash
```

Внутри контейнера:

```bash
cd /root/ros_ws
source /opt/ros/jazzy/setup.bash
colcon build --packages-select rail_stage1_interfaces rail_stage1
source install/setup.bash
```

Первый терминал: запустить только поиск/реестр и сервер подъезда.
Поиск остаётся выключенным, движение не начинается:

```bash
ros2 launch rail_stage1 rail_stage1.launch.py
```

Для следующих терминалов на хосте:

```bash
docker exec -it nav2_vlad_0 bash
source /opt/ros/jazzy/setup.bash
source /root/ros_ws/install/setup.bash
```

Второй терминал: запустить только сервер второго этапа. Движение
также не начинается до отправки действия:

```bash
ros2 launch rail_stage1 rail_entry.launch.py
```

В отдельном терминале отправлять команды этапов:

```bash
# 1. Включить поиск; исследовать вручную.
ros2 service call /rails/search/set_enabled std_srvs/srv/SetBool '{data: true}'
ros2 topic echo /rails/registry --once

# Выключить поиск после сохранения нужных объектов.
ros2 service call /rails/search/set_enabled std_srvs/srv/SetBool '{data: false}'

# 2. Подъезд к выбранным рельсам через Nav2; ID взять из реестра.
ros2 action send_goal /rails/approach rail_stage1_interfaces/action/ApproachRail \
  '{rail_id: rail_001}' --feedback

# 3. После успешного подъезда: выравнивание и прямой проезд.
ros2 action send_goal /rails/enter rail_stage1_interfaces/action/EnterRail \
  '{drive_distance: 1.5, drive_speed: 0.12}' --feedback

# Отмена текущего подъезда или текущего заезда соответственно.
# Пустое goal_info означает все активные цели данного действия.
ros2 service call /rails/approach/_action/cancel_goal action_msgs/srv/CancelGoal '{}'
ros2 service call /rails/enter/_action/cancel_goal action_msgs/srv/CancelGoal '{}'
```

Отключение поиска не отменяет действие движения. Для этого используются
указанные сервисы отмены.

## Визуализация

- `/rails/entry/debug_image`: исходный кадр (или маска, если RGB не
  пришёл с той же меткой времени), голубой целевой крест, зелёный
  центр перемычки, жёлтый отрезок ошибки, подпись dx/dy и yaw, фиолетовая стрелка направления рельсов. Обновляется
  в ALIGN; после перехода в DRIVE этот кадр остаётся последним кадром
  выравнивания. Текущую фазу смотреть в status или action feedback.
- `/rails/entry/status`: фаза, ошибки, дистанция, оставшееся время.
- `/rails/entry/drive_markers`: стрелка от начала прямого проезда до
  его целевой точки, в системе координат локализации.

Все отображения добавлены в `config/rails.rviz`. Можно подключить
соответствующие Image/MarkerArray к уже открытому RViz.

### Более быстрый переход ALIGN -> DRIVE

В `config/entry.yaml`: `alignment_tolerance_px: 12.0`, `alignment_frames: 3`,
`alignment_dwell_sec: 0.3`. При частоте масок около 5 Гц устойчивое попадание
подтверждается примерно за 0.4–0.5 секунды с первого подходящего кадра.
Выход за допуск и потеря свежего наблюдения по-прежнему сбрасывают подтверждение.
В `/rails/entry/status` доступны `alignment_frames`, `alignment_required_frames`,
`alignment_dwell_elapsed`, `alignment_tolerance_px`, `observation_valid` и
`pixel_error`. В лог пишется длительность ALIGN и ошибка при переходе в DRIVE.

### Проверка омни-обновления

33 unit-теста: три оси якобиана по численному движению камеры,
независимая коррекция бокового смещения, компенсация точки при повороте,

останавливает все оси. Физические команды движения агент не отправлял.

### Сегментация без ограничения частоты

Активный контейнер `rail_mask_vlad` использует код из
`~/projects/aida_nav_vlad/Roshack-yolodocker`. `max_rate:=0.0` отключает
программный ограничитель; входная очередь содержит один последний кадр.
Запуск из этой папки: `ROS_DOMAIN_ID=0 docker compose up -d --no-deps rail_mask`.
Один сегментатор на ROS-домен; исходный контейнер заменён экспериментальным.

Замер потока после снятия лимита: камера 30,0 Гц, маски 29,4 Гц;
медианная задержка маски 62,7 мс, p95 72,1 мс; YOLO 19,6 мс.
