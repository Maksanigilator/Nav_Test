# Поиск рельсов и отдельный подъезд: шаг 1

Вторая часть подготовлена отдельно: [совмещение точки, направления и прямой проезд](ENTRY.md).
Она запускается отдельным launch-файлом и отдельным действием `/rails/enter`.

Код находится в `~/projects/aida_nav_vlad/Nav_Test/src/rail_stage1`,
интерфейс действия — в соседнем `rail_stage1_interfaces`.
Камера, SLAM и Nav2 работают в исходном стеке. Сегментатор запущен
из новой копии в `rail_mask_vlad`, без лимита частоты (`max_rate:=0.0`).
Все команды запуска и работы по этапам: [основной README](../../../README.md).

## Модули

`rail_finder` не управляет движением. Поиск при запуске выключен.
Он принимает маску YOLO, выровненную глубину, CameraInfo и TF камеры.
Минимальная площадь маски задаётся в `config/rails.yaml`: `min_mask_area_px: 1200`.
Маска ниже порога не поступает в геометрическую обработку.

По глубине вне маски оценивается плоскость настила. Точки маски переводятся
в вид сверху с помощью TF и модели камеры; параметр `feature_height: 0.04`
компенсирует приблизительную высоту поверхности труб над настилом.
После скелетизации и Хафа требуются две примерно параллельные линии
на расстоянии колеи и третья поперечная линия у общего конца.
Прямая часть каждой линии должна быть не короче 25 см. Скругления
допускаются возле пересечений, но не заменяют недостающую линию.
Конкурирующие геометрические решения отклоняются.

Точка въезда — середина между пересечениями перемычки и обеих продольных
линий, спроецированная на плоскость настила. Направление идёт от перемычки
вдоль прямых участков. Для сохранения нужны пять независимых кадров
с согласованными положением и направлением. Точка и направление
преобразуются в `map` по TF на время кадра. При отсутствии TF `map`
наблюдение не сохраняется; подмена системой `odom` запрещена.

Реестр содержит ID каждого объекта, точку, yaw и количество подтверждений.
Повторное наблюдение уточняет объект; близкая оценка с противоположным
направлением не создаёт второй объект. JSON сохраняется атомарно в
`/datasets/rail_registry/rails_platform.json`, то есть в datasets новой
копии на хосте. Поиск можно выключить, не потеряв сохранённые объекты.
`map_id` защищает от загрузки реестра другой карты. При новом сеансе с
новым началом координат карты следует использовать другой map_id и файл.
Сохранённые точки пока не привязаны к ключевым кадрам SLAM и не
пересобираются автоматически после коррекции графа; новое наблюдение
уточняет положение в текущей карте.

`rail_approach` обслуживает отдельное действие `/rails/approach`.
По ID объекта он вычисляет `goal = entry - 0.90 * direction`, выставляет
ориентацию вдоль рельсов и передаёт цель в Nav2 `/navigate_to_pose`.
Передаёт feedback, результат и отмену; по таймауту отменяет свою цель.
Если завершение цели Nav2 не подтверждено, новые запросы блокируются
до перезапуска этого модуля. Прямых команд скорости нет.
Достижение точки подхода завершает действие. IBVS с боковым движением
и выравниванием направления реализован отдельно в `/rails/enter`.

## Сборка и запуск

Сборка внутри отдельного контейнера новой копии:

```bash
cd /root/ros_ws
source /opt/ros/jazzy/setup.bash
colcon build --packages-select rail_stage1_interfaces rail_stage1 maze_nav
source install/setup.bash
```

Для подключения только новых модулей к уже доступным камере, SLAM и Nav2:

```bash
ros2 launch rail_stage1 rail_stage1.launch.py rviz:=true
```

В новой копии `robot_nav.launch.py` также включает новые модули.
Старый сервер и накопление рельсов выключены аргументом `legacy_rails:=false`;
детектор кромки настила остаётся для построения карты.
Новый блок можно отключить `rail_stage1:=false`.
Дефолтный ROS_DOMAIN_ID новой копии — 43; камера и работающий стек
сейчас в домене 0. Для реального использования новые модули должны
работать в одном домене с источниками данных и Nav2. Не запускайте
второй драйвер камеры или второй навигационный стек для подключения
только этих двух модулей.

## Управление

```bash
# Включить поиск; движения эта команда не вызывает.
ros2 service call /rails/search/set_enabled std_srvs/srv/SetBool '{data: true}'

# Выключить поиск и сохранить найденные объекты.
ros2 service call /rails/search/set_enabled std_srvs/srv/SetBool '{data: false}'

# Посмотреть ID и координаты.
ros2 topic echo /rails/registry --once
ros2 topic echo /rails/search/status --once

# Отдельный запрос движения к точке перед въездом.
ros2 action send_goal /rails/approach rail_stage1_interfaces/action/ApproachRail \
  '{rail_id: rail_001}' --feedback
```

## RViz

В комплекте `config/rails.rviz`. Fixed Frame — `map`.

| Топик | Отображение |
| --- | --- |
| `/rails/approach_markers` | MarkerArray: зелёная точка въезда и направление; голубая цель подхода; соединяющий отрезок и ID |
| `/rails/approach_target` | Pose: фактически отправленная Nav2 цель, оранжевая стрелка |
| `/rails/search/debug_bev` | Image: проекция маски и три выбранные линии; при отказе UNCONFIRMED |
| `/rails/entry_observation` | Pose: текущее наблюдение до многокадрового подтверждения |

Маркеры и реестр публикуются с transient-local QoS и раз в секунду,
чтобы RViz мог подключиться после обнаружения и при выключенном поиске.
Отключение поиска оставляет подтверждённые маркеры.

## Проверено

В отдельном контейнере без сети и доступа к роботу:

- Восемь геометрических и файловых тестов: полная П при разных наклонах
  камеры; отказ для одной/двух линий, малой маски и отсутствующей глубины;
  независимые кадры, перезагрузка файла, разные карты, дедупликация и
  знак/расстояние точки подхода.
- Сборка обоих новых ROS-пакетов.
- ROS smoke test с фиктивным Nav2: включение/выключение, полный путь
  маска/глубина/TF → точка в map, сохранение, подъезд, отмена и неизвестный ID.
- Офлайн-прогон 13 старых семплов: две принятые тройки, остальные отклонены.
  Результаты в `Nav_Test/experiments/stage1_results`. Использован текущий
  TF камеры, поскольку старые снимки не содержат TF времени съёмки.
  Это диагностический прогон, не проверка точности положения в карте.

По отдельной команде оператора новые модули собраны и серверы запущены
в nav2_vlad_0: поиск выключен, сервер заезда в IDLE. Подъезд проверен оператором на роботе. Текущий омни-контроллер заезда
проверен агентом в тестах и изолированном ROS-домене; команды движения
агент не отправлял.

### Допуски предварительного подъезда

`rail_approach` проверяет фактический TF `map -> base_footprint`, а не длину
оставшегося пути из feedback Nav2. В `config/rails.yaml` заданы `xy_tolerance: 0.15`,
`yaw_tolerance_deg: 10.0`, `pose_dwell_sec: 0.3`, `pose_max_age_sec: 0.5`.
Нужны одновременно положение и угол, свежие независимые измерения и выдержка.
При достижении допуска отменяется только собственная цель NavigateToPose;
успех возвращается после терминального результата Nav2 и повторной проверки
позы. При неподтвержденной остановке блокировка движения сохраняется.
Глобальные допуски Nav2 не изменяются. Если Nav2 завершил цель сам, его результат
обрабатывается как прежде. Это предварительный подъезд; IBVS запускается отдельно.

Проверка обновления: 26 unit-тестов и ROS-тест в изолированном домене 211
с имитацией Nav2 (достижение допуска, отмена, ожидание остановки, удержание
motion lock, ошибка Nav2). Проверка движением на роботе не выполнялась.
