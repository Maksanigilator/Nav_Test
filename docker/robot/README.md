# `docker/robot` — навигация и детектор знаков на борту робота

Папка устроена так, чтобы её можно было **скопировать на Raspberry целиком
и больше ничего не переносить**: внутри и образ, и исходники, и запуск.
Репозиторий, интернет и реестр образов на роботе не нужны.

## Что здесь лежит

| Файл | Откуда берётся |
|---|---|
| `Dockerfile.arm` | в репозитории — рецепт образа с навигацией |
| `Dockerfile.yolo.arm` | в репозитории — рецепт образа с детектором знаков |
| `entrypoint.sh` | в репозитории — source ROS при входе (bash, не zsh) |
| `build.sh` | в репозитории — собирает образы и раскладывает папку |
| `run.sh` | в репозитории — навигация **на роботе** |
| `run_yolo.sh` | в репозитории — детектор знаков **на роботе** |
| `src/` | **создаётся сборкой** — копия `src/` проекта |
| `nav2-arm64.tar.gz` | **создаётся сборкой** — образ навигации |
| `yolo-arm64.tar.gz` | **создаётся сборкой** — образ детектора |
| `BUILD_INFO` | **создаётся сборкой** — дата, коммит, размеры |

Последние четыре в git не попадают: они целиком воспроизводятся из `build.sh`.

## Почему образов два

Детектор живёт отдельно от навигации, и на то три причины:

* torch с ultralytics весят больше, чем вся навигация. Навигационный образ
  пересобирается от каждой правки YAML — таскать через эмуляцию лишний
  гигабайт при каждой такой сборке незачем;
* установка torch под qemu — самое хрупкое место сборки, у нас уже дважды
  разваливался pip на таймауте к `files.pythonhosted.org`. Пусть его падение
  не блокирует доставку навигации;
* детектор нужен не всегда. Проехать полигон без знаков можно, и тогда этот
  образ на робота просто не везут.

## На ноутбуке

```bash
./docker/robot/build.sh                     # собрать оба образа и разложить
./docker/robot/build.sh --only nav2         # только навигация
./docker/robot/build.sh --only yolo         # только детектор знаков
./docker/robot/build.sh --send pi@10.0.0.5  # плюс отправить на робота
./docker/robot/build.sh --sync              # только обновить копию src/
```

Сборка идёт через эмуляцию qemu и занимает десятки минут — почти всё время
уходит на `apt` внутри arm64. Собирать на самой плате было бы в разы дольше.

Перенести можно и руками, папка самодостаточна:

```bash
rsync -a --partial --progress docker/robot/ pi@10.0.0.5:nav2_robot/
```

## На роботе

Заходить с пробросом X — тогда окна откроются здесь, а покажутся на ноутбуке:

```bash
ssh -X pi@10.0.0.5
cd ~/nav2_robot
./run.sh
```

Первый запуск сам выполнит `docker load` из архива — это пара минут, дальше
контейнер стартует мгновенно. Внутри:

```bash
colcon build --packages-select maze_nav
source install/setup.bash
ros2 launch maze_nav city.launch.py
```

Это поднимает всё сразу: Nav2, AMCL, исполнитель маршрута, RViz и редактор
графа. Ноутбук в этой схеме — только экран, ни одного узла на нём нет.

Если окна не открылись:

| Симптом | Причина |
|---|---|
| `cannot open display` | зашли без `-X`, либо на роботе не стоит `xauth` (`sudo apt install xauth`) |
| RViz падает на старте | не подхватился программный OpenGL; проверить `glxinfo \| grep "OpenGL renderer"`, должен быть llvmpipe |
| окна есть, но всё ползёт | так и будет: картинка рендерится процессором Pi и едет по Wi-Fi целыми кадрами |

Навигации графика не нужна — без `ssh -X` всё едет так же, просто молча:

```bash
ros2 launch maze_nav city.launch.py rviz:=false editor:=false
```

## Детектор знаков

Вторым терминалом, рядом с навигацией:

```bash
cd ~/nav2_robot && ./run_yolo.sh
```

Кадры берутся **прямо с USB-камеры**, а не по HTTP: детектор теперь на том
же железе, что и камера, и гонять картинки через сетевой сервер на самом
себе незачем. Заодно исчезли прокси, таймауты и разбор MJPEG — половина
причин, по которым детектор раньше падал.

Из этого следует важное ограничение: **`sign_camera.py` одновременно
работать не может**. `/dev/video0` отдаётся одному процессу, и тот, кто
пришёл вторым, получит «Device or resource busy». Либо детектор на роботе,
либо трансляция на ноутбук.

Проверить без навигации:

```bash
ros2 service call /detect_signs std_srvs/srv/Trigger
ros2 topic echo /sign_detected --once
```

Кадр с нарисованными рамками пишется в `src/yolo/last_detection.jpg` —
папка примонтирована, файл видно прямо с Raspberry.

Инференс идёт на процессоре. Замер на процессоре ноутбука: полный запрос
(три кадра с камеры плюс инференс) занял **1.5 с**, из них полсекунды —
паузы между снимками. На Cortex-A76 у Pi 5 будет заметно дольше, во
сколько раз — покажет замер на месте; ориентироваться стоит на единицы
секунд. Робот в этот момент стоит у точки, так что это не мешает.
Если покажется медленным, крутить `imgsz` и `burst`:

```bash
./run_yolo.sh python3 /root/ros_ws/src/yolo/sign_detector.py --ros-args \
    -p source:=camera -p device:=cpu -p imgsz:=480 -p burst:=2
```

## Что в образе и чего в нём нет

В образе нет ни `ros-jazzy-navigation2`, ни `ros-jazzy-nav2-bringup` —
поставлены только те пакеты Nav2, узлы которых реально запускаются.
RViz и PyQt5 есть: интерфейс работает на роботе и отдаётся по X11.

Метапакеты тянут за собой много лишнего:

| Метапакет | Что приезжает вместе с ним |
|---|---|
| `nav2-bringup` | `nav2-minimal-tb3-sim`, `nav2-minimal-tb4-sim`, `ros-gz-sim`, `ros-gz-bridge` — Gazebo целиком с `gz-ogre-next` и движком DART, плюс `slam-toolbox`, `diff-drive-controller`, `xacro` |
| `navigation2` | `nav2-rviz-plugins`, а с ними весь X-стек; плюс планировщики и контроллеры (`mppi`, `smac`, `theta-star`, `dwb`, `graceful`), `nav2-route`, `opennav-docking` — ничего из этого наш конфиг не включает |

Из графики на борту нужен один `rviz2` — он и поставлен напрямую, вместе
с `python3-pyqt5` для редактора маршрута и `libgl1-mesa-dri` ради
программного растеризатора: GPU у Pi 5 не дотягивает до OpenGL 3.3,
которого просит Ogre внутри RViz.

Цена решения — штатный `bringup_launch.py` здесь не запустится. Вместо
него `maze_nav/launch/nav2_frob.launch.py`: тот же набор узлов, только
перечисленный руками, без `route_server` и `docking_server`. `city.launch.py`
пользуется им и на ноутбуке тоже — чтобы стек на борту и на столе был один
и тот же, а не расходился незаметно.

| Убрано | Оставлено |
|---|---|
| Gazebo, DART, gz-ogre-next | все 15 пакетов Nav2, которые запускает наш launch |
| slam-toolbox, ros2_control | rviz2 + rviz_default_plugins |
| mppi, smac, theta-star, dwb, graceful | navfn, Pure Pursuit, Rotation Shim |
| nav2-route, opennav-docking | python3-pyqt5, libgl1-mesa-dri |

## Почему код не вшит в образ

Образ содержит только систему: ROS, Nav2, зависимости. Код проекта
монтируется с хоста из соседней папки `src/`.

Так правка параметра Nav2 доезжает до робота копированием одного файла:

```bash
scp src/maze_nav/params/frob_params.yaml pi@10.0.0.5:nav2_robot/src/maze_nav/params/
```

Если бы код лежал внутри образа, за каждую такую строчку пришлось бы платить
пересборкой arm64 под эмуляцией и перегоном двух гигабайт по Wi-Fi.

Плата за это — дублирование: `docker/robot/src/` копия `src/`. Копия
обновляется на каждой сборке и одной командой `build.sh --sync`,
редактировать её руками не нужно — правки надо вносить в оригинал.

## Как ещё переносят контейнеры

| Команда | Что переносит | Годится ли |
|---|---|---|
| `docker save` / `load` | образ со слоями, `ENTRYPOINT`, переменными | да, это и делает `build.sh` |
| `docker export` / `import` | файловую систему контейнера одним слоем | нет: теряются точка входа и переменные |
| `docker commit` | состояние контейнера в новый образ | только на разок: изменения не описаны в Dockerfile |
| реестр (`docker push`/`pull`) | образ через сервер | для одного робота разворачивать незачем |
